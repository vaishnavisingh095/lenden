# Engineering Code of Conduct — Lenden

This document defines how engineering work is done in this repository. It is
not a community conduct policy. It is an engineering standard, and it applies
to every contributor — human or AI — making changes here.

Lenden records other people's money. A business owner's outstanding balance,
a customer's payment promise, a recorded transaction — these are not sample
data. Treat every change with that in mind.

## Evidence over assumption

Never claim something works without having run or inspected it. Never invent
test results, runtime behavior, API responses, deployment behavior, or
performance numbers. If you did not execute it, you do not know it works.

When reporting on the state of the system, distinguish explicitly between:

- **FACT** — verified by reading the actual code or schema in this repo.
- **OBSERVATION** — verified by actually running something (a test, a query,
  a request) and recording what happened.
- **INFERENCE** — a conclusion drawn from facts/observations, clearly
  labeled as reasoning rather than something directly witnessed.
- **ASSUMPTION** — something taken as true without verification, and named
  as such.
- **RECOMMENDATION** — a proposed course of action, not a statement of what
  currently is.

If something is unknown, say "this is unknown" or "this requires runtime
verification." Do not fill the gap with a plausible-sounding guess.

## No AI slop

Code and documentation exist to do a job, not to look sophisticated. Being
generated by an AI is not an excuse for either failure mode below — hold
AI-written work to the same bar as anything else in this repo.

Do not:

- add unnecessary abstractions, wrapper layers, or indirection without a
  real, current responsibility
- add unnecessary services, dependencies, or infrastructure
- introduce generic factories/managers/helpers whose only purpose is to make
  the code look architectural
- write comments that restate what the code already says
- produce vague documentation that could apply to any project
- use buzzwords without explaining the concrete engineering reason behind
  them
- claim "production-ready," "scalable," "secure," or "robust" without
  evidence backing the specific claim
- write tests whose only purpose is increasing the test count
- optimize before there is a demonstrated need to
- rewrite working code for stylistic preference alone
- split files or components solely to make the architecture look more
  impressive than it is

Prefer:

- the smallest correct solution to the actual problem
- explicit code over clever code
- this project's existing patterns over introducing new ones
- changes justified by evidence, not by convention or trend
- tests that protect a real invariant, not tests for their own sake
- clear, deliberate failure handling
- simple architecture with strong invariants over elaborate architecture
  with weak ones

## Financial correctness

Lenden handles financial information: amounts, transactions, payments,
outstanding balances, promises, customer identity, and promise fulfillment.
All of it is correctness-sensitive.

Ambiguity must never be silently converted into a financial fact. If an
input is unclear — an unrecognized type, a missing amount, an uncertain
customer match — the system must surface that uncertainty, not resolve it
by picking whichever interpretation is easiest to implement.

AI output is not inherently trustworthy. An extracted amount, a
transliterated name, a parsed date — all of it is a proposal, not a
recorded fact, until it has passed validation and, where applicable, been
confirmed by the business owner.

## AI boundary

AI may interpret unstructured input (voice, natural language, ambiguous
phrasing). AI must never become the system of record on its own.

The application must preserve this chain, in order, for every financial
event:

**AI interpretation → user review/confirmation → application validation →
persistent state.**

No step in that chain may be skipped because it would be more convenient to
skip it.

## Failure-first engineering

Before considering a meaningful change complete, consider what happens
under:

- duplicate requests
- concurrent requests
- retries
- partial failures
- malformed AI responses
- missing data
- stale data
- invalid inputs
- database failures
- external dependency failures
- ambiguous outcomes (did the write succeed or not?)
- boundary values (zero, negative, very large, null)

A change that only handles the happy path is not finished.

## Invariants

Changes must preserve the invariants this system depends on, including:

- a rejected financial event must not mutate financial state
- a duplicate logical event must not create a duplicate financial record
- a failed operation must not leave misleading partial state behind
- a derived balance must remain consistent with the transaction records it
  is derived from
- server-side validation cannot be bypassed by manipulating a client
  request
- AI interpretation cannot directly mutate persistent financial state

If a change touches one of these, say so explicitly and show how the
invariant still holds afterward.

## Scope discipline

Every proposed feature must justify, in concrete terms:

- user value
- judging value
- engineering value
- implementation cost
- correctness risk
- regression risk

Shipping fewer features correctly beats shipping many features shallowly.
A hackathon deadline is a reason to cut scope, not a reason to cut
correctness.

## Git discipline

Commits must:

- represent one coherent milestone
- carry a meaningful message describing why the change was made
- avoid bundling unrelated changes together
- include the tests relevant to what changed
- preserve a history that a future reader can actually follow

Never commit generated noise, debugging artifacts, secrets, or unrelated
formatting churn.
